## 一、张芮萌（组长）开场 + 项目总体（约 2 分钟）

各位老师好，我们是第 4 组。我们本次汇报的是《东软电动汽车充电桩应用管理平台》的需求分析。下面我用一分钟介绍项目背景和总体方案，其余时间介绍我们组的项目管理与团队组织。

这个项目的出发点很明确：现在电动汽车保有量越来越大，但车主普遍遇到“找桩难、充电排队、价格不透明”的问题；而运营商这边，站点分布不均、设备利用率低、运营数据分散。所以我们希望做一套覆盖“用户端—服务端—数据端”的完整业务系统，再加上 Web 大屏和机器学习两个智能化子系统，实现从找桩、充电、结算，到运营管理和负荷预测的全链路闭环。

技术上按课程要求采用 Linux 下的 Qt 6 + C++ 开发，数据库用 SQLite，通信用 Socket，配合多线程；大屏用 ECharts，导航调用腾讯地图。开发环境是 Ubuntu 22.04 + Qt 6.2.4，都已经在本机验证可运行。

在项目管理部分，我们按照项目说明书建立了开发体制：我作为组长统筹进度，葛伊诺、毛悦琮、陈庚泉、吴羽桐分别承担用户端、服务器端、数据库和智能化模块；评审由专人把关，代码统一用 Git 管理，需求矩阵、设计文档、测试记录都会纳入版本库，保证过程可追溯。需求矩阵一共 23 项任务，其中标注“▲”的必修模块共 11 项，已全部拆解到个人并给出预计完成日期，整体排期覆盖到 9 月 10 号的答辩节点。

一句话总结我们组的思路：需求一次定全，模块开头定好，按依赖顺序推进，不做半截功能。下面请葛伊诺介绍充电用户端。

## 二、葛伊诺：充电用户端需求（约 2 分钟）

大家好，我负责的是充电用户端。用户端是用 Qt 在 Linux 桌面模拟手机端的体验，面向电动车车主，包含四个必修功能。

第一，附近充电站查询。用户进入系统后，可以选择区域或手动输入地址，软件层面模拟 GPS 定位，再调用腾讯地图 Web API 把地址转成经纬度；系统按距离从近到远展示充电站卡片，卡片上能看到站名、电价、电桩总数和空闲数量、距离。点击充电站还能查看每根电桩的编号、类型、状态和功率。

第二，一键导航。用户在电站列表点距离信息，就会用 QWebEngineView 加载腾讯地图，输入起点和终点，支持驾车、步行两种方式，直接跳到路线规划页。

第三，用户信息维护。采用 11 位手机号免密登录：手机号存在就直接登录，不存在就自动注册，默认昵称是“用户加手机号后四位”；还支持头像上传、昵称修改和余额充值，充值是模拟支付。

第四，电动汽车充电，这是用户端最核心、工作量最大的一块。进入充电页会先检查有没有“充电中”的未完成订单，有就弹窗提示并强制跳去结算，避免用户重复下单；没有才进入正常流程，选择空闲电桩、开始充电、计费、结算，余额实时更新。

这一部分依赖数据库里的电站、电桩、用户和订单表，所以我会等数据库结构确定后同步开发。界面样式参考了项目说明书里的用户界面示例，用布局管理器加 QSS 美化。我的介绍完了，谢谢。

## 三、毛悦琮：PC 服务器端基础管理需求（约 2 分钟）

大家好，我负责 PC 服务器端的基础管理和经营模块，共四个必修功能，都是给运营管理员用的宽屏后台。

第一，管理员登录。账号密码存在数据库的管理员表里，默认初始账号 admin、密码 123456，登录成功后进入管理后台。

第二，销售业绩。这个功能要体现运营价值：用 Qt 的 QChart 组件画近 7 日和近 30 日两条营收趋势折线图，同时展示今日营收、本月营收、总营收三个核心指标，并且支持时间维度切换。营收按“已完成”的充电订单汇总。

第三，电桩状态。用表格直观展示当前所有电桩的状态分布：在用、闲置、故障，各有多少、占比多少，让管理员一眼看出设备整体健康度。

第四，充电桩管理。列表展示电桩编号、所属电站、快充慢充类型、功率、当前状态、累计充电次数和时长；管理员选中电桩后可以远程重启，用来处理死机这类异常，这里我们按需求做模拟指令下发。

这个模块会用到 QChart、QTableWidget 和 SQLite 的聚合查询，金额这类数据我们会按“分”存储避免浮点误差，查询口径会按我们组统一的接口约定来做。介绍完毕，谢谢。

## 四、陈庚泉：充电站/用户管理 + 数据库端需求（约 2 分钟）

大家好，我负责两部分：一部分是服务器端面向业务管理的功能，另一部分是数据库端，也就是全组的地基。

先说充电站管理：管理员能查看所有电站的 ID、站名、地址、经纬度、总桩数和在线率，点进一个电站可以看到它下面每根电桩的实时状态；同时支持新增电站，填写站名、地址、经纬度和电桩数量，这里是模拟新增。

然后是用户管理：列表展示用户 ID、手机号、昵称、余额、注册时间和状态；支持冻结和解冻账号，用于风控场景；还支持按手机号模糊搜索。

再讲数据库端。我们要建用户、充电站、充电桩、充电订单、管理员五类核心表，另外为了支撑两个创新点，还设计了营销策略表、电桩健康阈值表和功率日志表，一共八张表，已经写成 schema.sql 并在 sqlite 里验证通过。表设计遵循规范：表名字段名小写、字段有明确含义、金额按分存储、时间统一本地时间。

通信部分我们定义统一的数据结构，字段命名和协议先在 common 公共头文件里定好，安全上强调参数绑定防 SQL 注入、输入校验和权限控制。需要说明的是：schema 和通信协议是全组的公共契约，我会在 9 月 5 号前合入主分支，作为大家开工的基础，所以请各位同学以我的建表脚本为准，不要各自改表。谢谢。

## 五、吴羽桐：大屏 + 机器学习 + 基础技术需求（约 2 分钟）

大家好，我负责三块：Web 大屏、机器学习智能分析，以及 Socket 通信、多线程、界面规范这些基础技术。

Web 大屏是给决策者看的运营健康度看板，用 ECharts 实现，流程上覆盖数据采集、存储、预处理、分析、可视化和模型部署，展示营收趋势、电桩状态、订单量这些实时指标。大屏是 Web 页面，用浏览器打开，ECharts 库会下载到本地，保证离线也能演示。

机器学习这边对应需求矩阵里带“▲”的充电负荷智能预测：我们希望基于历史充电时段、时长、电量，以及出行时段、天气、节假日这些数据做时序预测，输出未来 1 小时、6 小时、24 小时的站点负荷、空闲桩数量和高峰时段，结果给用户端推荐低拥堵电站、给运营端做负荷预警。考虑到实训环境和数据规模，我们会在 Qt/C++ 里用简化模型实现，比如移动平均和最小二乘回归，用 QChart 展示历史与预测曲线，不依赖外部机器学习框架，保证可演示。

基础技术方面，我会封装 Socket 通信组件和多线程工具供各端复用，统一各端界面用布局管理器加 QSS 的规范；错误处理我们组已经有公共组件，各端接入即可。

我的模块和组长的两个创新点有直接接口关系：预测结果会写进营销策略表和健康阈值表，供动态计费和自愈告警使用，所以这部分我会按排期优先完成。介绍完毕，谢谢。

## 八、可能提问与应答要点

**Q1：为什么用 Qt/C++，不用网页做？**
答：课程要求 Linux+Qt 开发，且 Qt 跨平台、适合桌面与嵌入式；桌面程序 + Web 大屏组合也符合项目说明书的技术路线。

**Q2：没有网、没有腾讯地图 key 怎么办？**
答：定位本身是软件模拟 GPS；地图导航我们会做降级处理，无网时显示提示或模拟页面，保证演示不中断。

**Q3：机器学习具体怎么做？数据从哪来？**
答：实训采用简化模型（移动平均/最小二乘回归），数据来自系统历史订单与桩日志，可生成演示数据；预测结果落到 SQLite 表，供创新点使用。

**Q4：五个人怎么协作不冲突？**
答：Git 分支管理，每人一个 feat 分支，公共契约（schema/common）统一由负责人合入 main 并评审，避免各改各的表。

**Q5：8 天时间来得及吗？**
答：核心必修功能优先（▲ 模块全部排进 09-07 中期演示），数据库先行、各端并行；创新点作为加分项排在后期，不影响必修闭环。

**Q6：数据安全怎么考虑？**
答：SQL 参数绑定防注入、管理员权限控制、用户敏感数据（手机号等）展示脱敏、通信数据做校验。
