## 一、张芮萌（组长）：开场与整体架构（PPT P01–P02，约 2 分钟）

各位老师好，我们是第 4 组，今天做结题答辩。我们的项目是《东软电动汽车充电桩应用管理平台》，目标是把"用户端、服务器端、数据库、机器学习、Web 大屏"五个部分串成一个真正能跑通的运营闭环。(PPT P01)

先说结论：需求矩阵 23 项全部落地，带▲的必修模块全部实现并合入主干 main，两个创新点已经从"模拟触发"升级为"预测驱动"的真实机制，主干始终可编译可运行，自动化测试一共 132 项全部通过，仓库是公开的。(PPT P02)

整体架构是这样的：(展示：P02 的五端架构图) 用户端用 Qt/C++ 写，负责扫码充电、找桩、导航和个人中心；服务器端同样是 Qt/C++，用 Socket 9999 做设备会话，用 HTTP 8890 对外提供数据聚合；数据库用 SQLite，一共 8 张表；机器学习子系统用 C++ 实现负荷预测，输出给大屏和计费使用；Web 大屏用本地离线的 ECharts 5.6.1 做实时看板。这五端不是各写各的，数据是通的——一条充电订单会从用户端发起，经服务器落库，最后出现在大屏上。

下面按"一页一个功能"的顺序，请各位同学演示自己负责的模块。

## 二、葛伊诺：充电用户端（PPT P03–P06，约 2 分钟）

大家好，我负责充电用户端，演示四个功能。(展示：运行中的用户端 UserClient)

第一个是**附近电站查询**。(PPT P03) 进入后系统先做 IP 定位，再调用地点搜索，返回周边 5 公里内真实的充电站，列表里能看到名称、地址和距离。(展示：电站列表页) 每个电站还实时显示价格和空闲桩数，如果有电站正在做闲时优惠，会打上"闲时特惠"的徽标。这里我做了双通道兜底：先地址解析，失败自动回退地点搜索；断网时会给出降级提示，不会崩溃。

第二个是**一键导航**。(PPT P04) 在电站详情页点"一键导航"，会展示静态地图和驾车路线，自动算出距离和用时。(展示：导航页) 地图在外部不可用时能降级到静态图，保证演示不中断。

第三个是**用户维护**。(PPT P05) 手机号登录时，没注册过的号码会自动注册，注册即生成昵称和初始余额。(展示：手机号登录 → 自动注册) 登录态、余额、昵称会实时同步到"我的"页面。(展示：我的页面)

第四个是**电动汽车充电**，也就是整条闭环。(PPT P06) 在电站详情里选一根桩启动充电，页面上实时显示已充电量和费用；结束充电后自动结算并生成订单，上报给服务器端。(展示：充电中 → 结算完成) 服务器端把订单落库，同时累加到今日营收和今日用电量，最后出现在大屏上。这样"用户端发起 → 服务器处理 → 数据库落地 → 大屏展示"这条链路是完整可追的。

## 三、毛悦琮：PC 服务器端（PPT P07、P09、P10，约 2 分钟）

大家好，我负责服务器端的登录、销售业绩、电桩状态和充电桩、用户管理。(展示：运行中的 PcServer)

先是**管理员登录和销售业绩**。(PPT P07) 管理员登录后进入运营管理界面，销售业绩用 QChart 画近 7 日和近 30 日的营收折线，统计今日、本月、累计三项指标，数据都来自订单表的聚合查询。(展示：登录 → 业绩看板 → 切换 7/30 日)

然后是**充电桩管理**。(PPT P09) 电桩状态做三级分级，正常、预警、故障，颜色随级别加深；管理员可以对单根桩下发远程重启指令，指令经 Socket 传到设备侧。(展示：桩列表 → 选中故障桩 → 远程重启 → 状态恢复) 这个远程重启还和后面的自愈创新点联动，稍后组长会演示。

最后是**用户管理**。(PPT P10) 用户列表支持搜索、冻结和解冻，被冻结的用户无法登录、无法发起充电，状态会即时写回数据库。(展示：搜索用户 → 冻结 → 该用户登录被拒)

## 四、陈庚泉：数据库端与充电站管理（PPT P08、P11，约 1 分半）

大家好，我负责数据库端和充电站管理。(展示：运行中的 PcServer 日志"建库完成")

先讲**数据库设计**。(PPT P11) 一共 8 张表：电站、电桩、订单、用户、管理员五类核心表，加上营销策略、健康阈值、功率日志三张支撑表。金额一律按"分"存整数，避免浮点误差；所有查询参数化，防注入；外键和索引都建好了，还配了数据库契约测试。(展示：sqlite3 `.tables` 显示 8 张表 + 契约测试通过) 服务器启动时自动建表并写入演示数据，就算空库也能一键跑起来。

## 五、吴羽桐：机器学习与 Web 大屏（PPT P12–P13，约 2 分钟）

大家好，我负责机器学习简化和 Web 大屏。(展示：浏览器打开大屏)

先是**负荷预测**。(PPT P12) 我用历史充电功率做聚合，用 OLS 最小二乘加 WMA 加权移动平均做时序预测，输出未来 6 小时的负荷曲线和峰值，写进数据库，供大屏和计费使用。(展示：预测曲线图) 这里做了个保护：样本不足的时候自动回退到确定性的日曲线，保证任何情况下都有输出。

然后是**Web 运营大屏**。(PPT P13) 这一版大屏我们改成了**书签分页**：顶部三个书签——总览、负荷预测、营收订单，点哪个切哪页，切换带淡入动画，一页只讲一个主题，不会把所有图表挤在一屏。(展示：依次点三个书签切换) 总览页上是六张 KPI 卡——设备规模、健康率、异常待检修、今日营收、实时负荷、未来 6 小时预测峰值，下面配一个电桩状态的环形图。(展示：总览页) 大屏每 10 秒轮询一次 8890 聚合接口，服务断开时会自动回退到离线快照，不会白屏。(展示：断掉服务后大屏仍显示数据) 配色统一成莫兰迪绿，按深浅和透明度分层，ECharts 放在本地 vendor 目录，完全离线，双击就能打开。

## 六、张芮萌（组长）：创新点与总结（PPT P14–P15，约 2 分钟）

最后我来讲两个创新点，它们也是我们和"普通作业版"最大的区别。

**创新点一，闲时动态计费。**(PPT P14) 原来的计费是固定单价，运营端没法引导错峰，用户端也没有价格弹性。我们把机器学习预测的**未来 1 小时空闲率**直接接进业务：当某个电站预测空闲率大于 60% 时，系统自动把该站价格打到 8 折，并实时推送到用户端电站详情页，标上"闲时特惠"；空闲率回落就自动恢复基础价。(展示：空闲率 80% → 显示"闲时特惠"；30% → 恢复基础价) 这样就形成了"预测 → 定价 → 用户端展示"的完整业务闭环，而不是只画一条预测曲线。

**创新点二，异常自愈告警。**(PPT P15) 原来的故障处理是人工上报加手动重启，属于被动响应。我们用历史充电功率给每根桩算出一个正常波动阈值，服务器端跑一个"自愈检查"定时任务，把实时数据和阈值比对，做正常、预警、故障三级分级；当某根桩连续 3 次功率低于历史均值的 20%，系统不等人工介入，自动标记"需检查"并触发一次模拟远程重启。(展示：连点三次模拟异常 → 自愈日志 → 自动重启 → 恢复正常)

这两个创新点加起来，把大屏的"展示"变成了会真正驱动业务动作的能力：预测不只用来画曲线，而是**用来定价、用来运维**。

总结一下：需求矩阵 23 项全部闭环，带▲的必修模块全部实现，两个创新点从模拟升级为预测驱动的真实机制，主干可编译可运行，132 项自动化测试全部通过。以上是第 4 组的结题汇报，谢谢各位老师，请批评指正。

## 附：可能提问与应答要点

- **创新点是真实的还是演示的？** 机制真实、可现场跑通：预测结果写库、策略引擎读库定价、用户端读库展示；自愈定时任务真实比对阈值并触发重启流程。数据为演示口径，链路是真实的。
- **为什么用 OLS + WMA，而不是更复杂的模型？** 课程要求与数据量决定：样本有限，OLS 加加权移动平均稳定、可解释、可离线跑；接口留了扩展点，后续可替换更强模型。
- **大屏为什么改成书签分页？** 一屏塞满图表既挤又看不清；按主题分页（总览/负荷预测/营收订单）更聚焦，也便于逐页讲解；切换时图表自动 resize，不会出现空白。
- **8 张表够用吗？会不会太少？** 覆盖了"用户—电站—电桩—订单—管理员"主链，外加营销策略、健康阈值、功率日志三张支撑表，正好支撑两个创新点；表少但约束齐全，反而好维护。
- **用户端价格/桩数是不是模拟值？** 地点搜索只提供基础信息，价格与空闲桩数由服务器/数据库提供；闲时优惠由预测驱动，已在矩阵里写明数据口径。
- **离线可用吗？** 大屏 ECharts 为本地 vendor，可离线双击打开；服务断开自动回退离线快照。用户端地图与定位有降级通道，不会崩溃。
- **测试覆盖到什么程度？** 全仓 132 项自动化测试，覆盖数据库、充电站/桩/用户管理、Web 大屏接口、负荷预测与 Socket 会话等关键路径。
