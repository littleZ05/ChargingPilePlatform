# 第二阶段 · 数据来源、处理链路与字段定义

> 状态：**已确认（2026-09-18）**，对应清洗规则版本 `rule_version = 2.0`。
> 代码唯一真源：`stage2/common/contract.py`；人读唯一真源：本文件。两处必须一致，改一处必须改另一处。
> 与之互为约束的文档：`boundary.md`（使用边界）、`api.md`（接口字段）、`dashboard/接口与指标约定.md`、`cleaning/README.md`、产物中的 `数据字典.md`。

本文件按"数据从哪来 → 怎么处理 → 每个字段怎么得到 → 怎么校验 → 哪些话不能说"的顺序写完整链路，
目的是让任何一个数字都能沿这条线回溯到源头。

清洗环节按课程要求的六步流程执行：**探查 → 质量评估 → 制定规则 → 执行 → 校验 → 报告**。
其中"校验"包含三层对账：输入行数 = 保留 + 隔离；六张 ADS 聚合表与 DWD 的会话数、电量、费用逐项相等；
同输入重复运行的输出可复现（哈希一致）。具体规则清单在 `cleaning/README.md`。

## 三、字段定义

### 3.1 `dwd/sessions.csv`（31 列）

原 28 列：`source_row, session_id, user_id, station_id, location_id, facility_type, facility_label, station_name, address, kwh, fee_original, fee_status, created_raw, ended_raw, calendar_date, timezone, start_hour, end_hour, weekday, weekday_index, weekend, duration_hours, platform, manager_vehicle, positive_energy, time_of_day_usable, weekday_usable, quality_flags`

本次新增 3 列：`time_period`、`unit_price`、`estimated_fee`（见 3.5）

非空约束：`session_id, user_id, station_id, kwh, duration_hours, start_hour, weekday, quality_flags`

派生字段：

- `positive_energy = kwh > 0`；`weekend = weekday_index >= 5`
- `time_of_day_usable` / `weekday_usable`：由源字段校验结果决定，为 1 才进入小时、星期维度统计
- `time_period`：由 `start_hour` 按时段表得到；小时校验未通过时留空，`unit_price`、`estimated_fee` 同样留空（**不用低谷值兜底**）
- `facility_label`：由桩类型码表得到，未收录编码写作 `待核编码N`

### 3.2 `dwd/stations.csv`（12 列）

`source_row, stationId, locationId, facilityType, station_name, address, device_count, open_time, update_time, facility_label, geography_status, quality_flags`

### 3.3 `dwd/battery.csv`（16 列）

`source_row, esd_raw, record_time_raw, timestamp, time_series_usable, soc_percent, pack_voltage_v, current_a, max_cell_voltage_v, min_cell_voltage_v, max_temperature_c, min_temperature_c, available_energy_source_unit_unverified, available_capacity_ah, instantaneous_power_magnitude_kw, quality_flags`

电池表与会话表**不建立关联**：`esd` 与 `sessionId` 数值重合不构成业务证据。

### 3.4 `ads/` 聚合表（6 张）

`by_station_id`、`by_facility_type`、`by_platform`、`by_start_hour`、`by_weekday`、`by_time_period`。
统一列：`dimension_value, session_count, positive_energy_count, zero_energy_count, total_kwh, source_fee_total_unverified, zero_fee_count, estimated_fee_total, duration_hours_total`。

### 3.5 派生字段的取值与来源

| 字段 | 取值 | 取值来源 |
|---|---|---|
| `facility_label`（桩类型） | 1=直流、2=交流、3=直交流一体 | 课程资料注释给出的码表；数据集里的编码 4 无对应标签，保留原编码并标注「待核编码4」 |
| `time_period`（峰谷时段） | 高峰 8–11、18–21；平时 12–17；低谷 0–7、22–23 | 课程资料注释给出的划分；按开始小时判定 |
| `unit_price`（分时电价） | 高峰 1.5 / 平时 1.0 / 低谷 0.7 元/kWh | **项目设定的参考电价**（来源为课程讨论中的取值）；老师原始材料中未收录这些数字，因此页面与报表一律标注为"参考估算值" |
| `estimated_fee`（估算电费） | `kwh × unit_price`，四舍五入到分 | 由上面两项派生，**不是真实收费、不计入营收**，与原费用字段分列呈现、不相加 |

`time_period` 是枚举字段，接口层统一使用 `peak` / `normal` / `off_peak`，中文标签只出现在展示层。

### 3.6 `manifest.json` 必需键

`rule_version, input_sha256, reconciliation{表→input/retained/quarantined}, total_kwh, fee_total_source_unverified, fee_total_estimated_model, output_sha256`

## 四、校验与失败行为

1. 任何进程读取清洗产物前**先做数据校验**（实现：`stage2/common/contract.py::load_cleaning`）：规则版本匹配、必需列齐全、行数与 `reconciliation` 一致、三张明细 SHA256 与清单一致、总电量/原费用/估算电费与清单一致，并对 `time_period`、`unit_price` 与 `start_hour` 做交叉校验。
2. 校验不通过时抛 `ContractError`，消息必须包含具体缺失项、期望版本与实际版本、以及修复命令（`bash stage2/run_all.sh`）。
3. **禁止**直接取字段导致 `KeyError`；**禁止**静默降级、补默认值、跳过该维度。
4. 大屏服务启动即校验：失败时打印原因并以非零码退出；运行期间数据被改坏，接口返回 **503 + 原因**（不伪装成参数错误）。
5. 前端读取失败时显示错误横幅与重跑命令，**不退回演示数据、不白屏**。

## 五、数据使用边界（不可越界表述）

1. `chargingFees` 原字段合计 401.52，**币种与语义未核实**，不得称为营收、收入或利润。
2. 会话年份原始值为 `0014`/`0015`，**不得改写为 2014/2015**，也不做真实日/月/年趋势。
3. `session_count` 是**会话次数**，不是充电桩数量，也不能等同成功支付订单数。
4. 零电量（55 条）与零费用（3016 条）**保留并标记**，不认定失败、免费或缺失。
5. `estimated_fee` 是按项目设定电价算出的参考值，**不是真实收费、不是营收**，必须与原费用字段分列呈现、不相加。
6. 桩类型中文标签是映射结果，编码 4 不并入任何一类、不猜语义。
7. 电池表不与会话表 JOIN；电池时间精度不可恢复，不做时间序列。
8. 课程数据集为郑州站点，**与第一阶段 Qt 演示站（北京）不是同一批站点**，两组数据不做合并统计。
9. 采集到的平台侧数据是**课程演示库**，其规模不代表真实生产量级。
